## Discovery and chosen workflow

Call 1 exposed `material_asset` with describe/read/validate/write/capture/apply. Call 3 describe gave a complete version-1 JSON example, units, image roots, file/target limits, and an explicit workflow. It stated that capture resolves inherited images and makes all five roles explicit; writing a definition leaves live copies unchanged; apply replaces complete factors, sampling, and images as one undoable operation, preserving meshes/transforms/pipeline handles and leaving copies independently editable. It explicitly said to reapply to read revisions. These statements were sufficient to choose a snapshot workflow without guessing whether saved assets were live-linked.

Discovery also supplied the live factor schema: base RGB is sRGB, alpha linear, emission linear HDR, UV rotation radians; base/metallic/roughness/AO/occlusion strength have 0..1 limits, alpha cutoff is nonnegative, normal scale is finite with typical 0..2. `material_asset.document` itself is only typed as an object, so its complete nested contract is supplied by returned examples and runtime validation rather than the discoverable nested schema. Query results exposed `material_editable`, including editable plinths as well as spheres; exact names let me choose sphere objects rather than their plinths.

`material` now also advertises texture assignment and per-role sampling authoring. I exercised reusable image/sampling authoring through material assets, not direct `set_texture` or `set_sampling`.

## Friction and preferred affordances

These are my preferences from this run, not claims about how LLMs generally behave:

- The explicit independent-copy contract and five-role capture were useful. I would keep them prominent: otherwise I would need to test whether revising a saved file automatically updates objects.
- Inspection and asset documents use different sampler names/shapes. Inspection has `wrap_u`, `magnification`, and `linear_mipmap_linear`; asset JSON has `address_u`, `mag_filter`, and separate min/mip filters. Returned asset JSON round-trips successfully, but copying an inspection object is not directly interchangeable. A shared authoring representation or an explicit conversion affordance would reduce translation.
- Discoverable nested document schema or field-level limits alongside `describe` would make definition editing more self-contained. The clear roughness rejection already makes recovery straightforward; structured field/path/received/allowed information would help automate it.
- Apply returns the full document and atomic/independent flags, but no per-target before/after summary. I used several additional inspect calls to establish independence. An optional compact receipt of changed factors, sampling roles, and image-source identities per target would reduce follow-up calls.
- I would like optional historical provenance identifying the last applied definition path plus a content fingerprint, explicitly informational rather than a live link. The current texture provenance explains image origins well, but an independently edited copy does not identify which saved definition originally supplied it. Format version 1 is not a content revision identifier.

## Limits of this evidence

The task worked through discovery alone: capture of effective imported maps, reuse on two meshes, independent file revision and deliberate application, validation recovery, local copy editing, native undo/redo appearance, and fresh-ID save/reload all have concrete evidence. Screenshots and receipts together establish these observed results, not shader or renderer correctness in every case. The combined amber factor/UV revision does not isolate each factor's or UV transform's rendering contribution. Five roles were transferred and reported, but I did not independently isolate each role's GPU sampling, neutral fallback capture, invalid-resource handling, direct texture assignment, normal-UV tangent restrictions, anisotropy clamping, or Scene/File-root portability to another project. Geometry/transform preservation was visually apparent and fresh query positions/bounds retained, but pipeline handle identity is only a tool contract and was not exposed for verification. No unsupported capabilities were assumed.
